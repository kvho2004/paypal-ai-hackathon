# APIMatic in Krumms

What we used from APIMatic, what we learned from its Context Plugin, and where the two did not line up. Everything here was checked against the repo and the installed packages on Nov 11, 2026.

## 1. The APIMatic-generated PayPal SDK is our PayPal layer

Every server-side PayPal call in Krumms goes through `@paypal/paypal-server-sdk` 2.5.0, which APIMatic generates (its controller files carry the header "This file was automatically generated by APIMATIC v3.0", and it runs on `@apimatic/core`).

| What Krumms does | SDK call | Our code |
|---|---|---|
| Read the student's purchase history | `TransactionSearchController.searchTransactions` | `lib/paypal/transactions.ts` |
| Create an order paid to Demo Diner | `OrdersController.createOrder` | `lib/paypal/orders.ts` |
| Capture an approved order | `OrdersController.captureOrder` | `lib/paypal/orders.ts` |
| Read back an already-captured order | `OrdersController.getOrder` | `lib/paypal/orders.ts` |
| Two clients, one per PayPal app (student and Demo Diner) | `Client` with `clientCredentialsAuthCredentials` | `lib/paypal/client.ts` |

What the generated SDK saved us:

- **Typed requests and responses.** Field names such as `purchaseUnits[].referenceId`, `payments.captures[]` and `transactionInfo.paypalReferenceId` came from the SDK's type definitions, so mistakes surfaced in `tsc` rather than at runtime.
- **Token handling.** The client fetches and refreshes OAuth tokens; we never wrote that code for the app.
- **Paging parameters for Transaction Search** (`pageSize`, `page`, `totalPages`) were typed, which made the 31-day window loop straightforward.

One thing it did not save us: in this SDK version an API failure throws an `ApiError` whose `message` is empty. We found that by testing and wrote a small `explain()` helper in `lib/paypal/orders.ts` that reports the HTTP status and PayPal's issue code (for example `PayPal API 422: ORDER_NOT_APPROVED`).

## 2. The Context Plugin

`npx context-plugins install paypal` was run on Nov 9. It installed plugin version 0.4.1 into Cursor and VS Code. It bundles skills for TypeScript, Python and C#, including getting started, client initialization, error handling and a PayPal integration workflow.

### What we found when we checked it against our code

**The plugin describes a different SDK than the one Krumms uses.**

| | Krumms today | What the plugin's skills describe |
|---|---|---|
| Package | `@paypal/paypal-server-sdk` 2.5.0 (npm) | `paypal`, installed from a GitHub repository branch |
| Entry point | `new Client(...)` plus `new OrdersController(client)` | `PaypalClient`, called as `client.{resource}.{operation}` |
| Errors | `ApiError` with `statusCode` and `result`; empty `message` | One error family with `err.kind`, `err.status`, `err.payload`, and a message such as "POST ... failed with 422" |

So the plugin's code-level guidance does not apply line for line to our PayPal code, and **our PayPal code was not generated through the plugin**. It was written against the installed SDK's type definitions and verified with real sandbox calls. We are stating this plainly rather than claiming the plugin wrote it.

We did not switch SDKs. The plugin's SDK installs from an unpinned Git branch, and replacing a working, tested payment path the day before the deadline was not a risk worth taking.

### What we did take from it

The plugin's integration workflow has a checklist for "durable writes" (anything that creates or changes something on PayPal's side). It applies whatever SDK you use, so we reviewed our checkout against it.

| Checklist question | Krumms |
|---|---|
| What stops the same payment being recorded twice? | `Purchase.paypalTxnId` is unique in the database, and `savePurchases` upserts by it |
| What happens if capture is called twice (double click, retry)? | PayPal answers `ORDER_ALREADY_CAPTURED`; `capturePayPalOrder` reads the order back and returns the same purchase. Tested: a second capture returned the same row |
| What if the capture response is lost after the buyer approved? | The approval card reports "failed" and tells the student to check their purchases before retrying. A webhook backup is planned but not built |
| Is the same payment counted again when it appears in Transaction Search under another id? | No. Ingestion skips entries whose `paypalReferenceId` matches a capture we already saved (`withoutKnownCaptures` in `lib/purchases.ts`) |
| Does each write carry an idempotency key? | **Gap.** The installed SDK accepts `paypalRequestId` on `createOrder` and `captureOrder`, and we do not set it. Capture is still safe because of the two rows above; a double-clicked create makes a second unpaid order, which is harmless |

The error-handling skill also confirmed the lesson from section 1: the newer generated SDK puts the method, URL and status into `err.message`, which is exactly what we had to add by hand with `explain()`.
